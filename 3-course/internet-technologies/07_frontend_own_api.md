# Занятие 7. Клиент и собственный API: fetch, Express и SQLite

## О занятии

В ЛР3 браузер отправлял HTTP-запросы к чужому API. В ЛР5 мы создали собственный сервер Express, а в ЛР6 научились сохранять его данные в SQLite.

Теперь соединим всё в одно приложение.

~~~text
пользователь нажимает кнопку
            ↓
JavaScript в браузере
            ↓
fetch() / HTTP / JSON
            ↓
Express-маршрут
            ↓
SQL-запрос
            ↓
SQLite
            ↓
JSON-ответ
            ↓
обновление интерфейса
~~~

В этой работе **не нужно создавать новый сервер или новую базу с нуля**. Возьмите работающий API из ЛР6 и добавьте к нему браузерный интерфейс.

---

# 1. Что уже умеет сервер

Предположим, ваш сервер обрабатывает задачи:

~~~text
GET    /api/tasks
GET    /api/tasks/:id
POST   /api/tasks
PATCH  /api/tasks/:id
DELETE /api/tasks/:id
~~~

Пример задачи:

~~~json
{
  "id": 5,
  "title": "Разобрать fetch",
  "description": "Связать браузер с сервером",
  "done": false
}
~~~

Вместо задач можно использовать собственную сущность из ЛР6. Тогда замените пути и имена полей на свои.

Раньше мы проверяли маршруты через браузер, curl или другой HTTP-клиент. Теперь запросы будет отправлять интерфейс нашей страницы.

# 3. Express может отдавать HTML, CSS и JavaScript

В server.js подключите модуль path и статические файлы:

~~~javascript
const path = require('node:path');

// После создания app:
app.use(express.static(path.join(__dirname, 'public')));
~~~

Это позволяет браузеру запрашивать:

~~~text
GET /
GET /style.css
GET /app.js
GET /api/tasks
~~~

Первые три запроса получают файлы интерфейса, четвёртый — данные из API.

Если сервер уже содержит app.use(express.json()), оставьте его: он нужен для чтения JSON-тела POST и PATCH.

Не создавайте отдельный второй Express-сервер только ради HTML.

# 4. Что делает fetch()

fetch() отправляет HTTP-запрос и возвращает Promise.

Пример:

~~~javascript
const response = await fetch('/api/tasks');
const tasks = await response.json();

console.log(tasks);
~~~

Разберём:

- /api/tasks — адрес маршрута на **том же** сервере;
- await fetch(...) — дождаться HTTP-ответа;
- response — объект Response с кодом статуса и заголовками;
- await response.json() — прочитать тело и преобразовать JSON в JavaScript-значение.

Здесь response.json() выполняется отдельно от fetch(), потому что сначала приходят HTTP-ответ и его заголовки, затем считывается тело.

Открывайте DevTools → Network, чтобы наблюдать оба направления обмена.

---

# 5. Почему нельзя проверять успех только через try/catch

Важная особенность: fetch() **не считает HTTP 400 или 404 сетевой ошибкой**.

Для ответа 404 Promise от fetch() обычно успешно выполняется; просто:

~~~javascript
response.ok === false
response.status === 404
~~~

Поэтому нужно явно проверять статус.

~~~javascript
async function loadTasks() {
  const response = await fetch('/api/tasks');

  if (!response.ok) {
    throw new Error('HTTP ' + response.status);
  }

  return response.json();
}
~~~

А вот при недоступном сервере fetch() может завершиться исключением.

Не смешивайте:

~~~text
404 — сервер ответил, но ресурс не найден
сервер выключен — запрос не смог успешно получить HTTP-ответ
~~~

# 6. Общая функция HTTP-запроса

Чтобы не повторять проверку ошибок в каждом обработчике, можно написать небольшую обёртку.

~~~javascript
async function request(url, options = {}) {
  const response = await fetch(url, options);

  if (!response.ok) {
    let message = 'HTTP ' + response.status;

    try {
      const data = await response.json();
      message = data.error || message;
    } catch {
      // Ответ с ошибкой мог не содержать JSON.
    }

    throw new Error(message);
  }

  if (response.status === 204) {
    return null;
  }

  return response.json();
}
~~~

Почему выделяем 204?

После успешного DELETE сервер в ЛР6 отвечает:

~~~javascript
res.status(204).end();
~~~

У такого ответа нет тела. Если всё равно вызвать response.json(), попытка разобрать пустой ответ приведёт к ошибке.

# 7. Откуда берётся состояние страницы

В ЛР2 мы уже отделяли данные от отображения:

~~~text
values[]
   ↓
render()
   ↓
DOM
~~~

Здесь принцип остаётся, но данные приходят с сервера:

~~~text
SQLite → API → tasks[] → render() → DOM
~~~

Пример:

~~~javascript
let tasks = [];

async function refreshTasks() {
  tasks = await request('/api/tasks');
  render();
}
~~~

**База данных — постоянный источник данных, а массив tasks — текущая копия для интерфейса.**

После успешного изменения через POST, PATCH или DELETE можно снова вызвать refreshTasks(), чтобы показать состояние, которое действительно хранит сервер.

# 8. Отображение списка

Минимальный HTML:

~~~html
<h1>Мои задачи</h1>

<form id="task-form">
  <input id="task-title" placeholder="Название">
  <button type="submit">Добавить</button>
</form>

<p id="message"></p>
<ul id="task-list"></ul>

<script src="/app.js"></script>
~~~

Пример безопасного вывода одного названия:

~~~javascript
function render() {
  const list = document.querySelector('#task-list');
  list.replaceChildren();

  for (const task of tasks) {
    const li = document.createElement('li');
    li.textContent = task.title;
    list.append(li);
  }
}
~~~

Здесь специально используется textContent.

Не вставляйте пользовательские названия через innerHTML: текст, пришедший с сервера, не должен интерпретироваться как HTML-разметка.

Позже вы дополните каждую строку кнопками изменения и удаления, признаком выполнения и другими полями своей сущности.

# 9. Создание записи: POST

POST отправляет данные в теле HTTP-запроса.

~~~javascript
async function createTask(title) {
  return request('/api/tasks', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      title,
      description: ''
    })
  });
}
~~~

Почему нужен JSON.stringify()?

Потому что body отправляется в виде текста JSON, а не как произвольный JavaScript-объект.

На сервере Express получит данные через:

~~~javascript
req.body.title
~~~

при условии, что подключён express.json().

Если создание прошло успешно, сервер вернёт 201 и новую запись с id, присвоенным базой данных.

---

# 10. Обработка отправки формы

У формы есть событие submit.

~~~javascript
const form = document.querySelector('#task-form');

form.addEventListener('submit', async event => {
  event.preventDefault();

  const input = document.querySelector('#task-title');
  const title = input.value.trim();

  if (!title) {
    showMessage('Введите название');
    return;
  }

  try {
    await createTask(title);
    input.value = '';
    await refreshTasks();
    showMessage('Запись добавлена');
  } catch (error) {
    showMessage(error.message);
  }
});
~~~

preventDefault() отменяет обычную отправку HTML-формы с перезагрузкой страницы.

При этом серверная проверка обязательного title **остаётся необходимой**. Клиентскую валидацию легко обойти, отправив запрос напрямую.

Функцию showMessage(message) реализуйте сами: она должна выводить сообщение пользователю.

---

# 11. Изменение записи: PATCH

Чтобы отметить задачу выполненной:

~~~javascript
async function setTaskDone(id, done) {
  await request('/api/tasks/' + id, {
    method: 'PATCH',
    headers: {
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({ done })
  });

  await refreshTasks();
}
~~~

PATCH меняет только переданные поля. Если отправить done, название и описание должны сохраниться.

Для другой сущности изменяйте своё поле: например available у книги или quantity у товара.

---

# 12. Удаление записи: DELETE

~~~javascript
async function deleteTask(id) {
  await request('/api/tasks/' + id, {
    method: 'DELETE'
  });

  await refreshTasks();
}
~~~

Обратите внимание: при успешном удалении ожидается 204 без тела.

Если ID не существует, сервер должен вернуть 404, а интерфейс — показать понятное сообщение.

---

# 13. Обработка ошибок и состояний загрузки

Пользователь должен понимать, что происходит, даже если запрос не удался.

Предусмотрите как минимум:

~~~text
загрузка...
данные загружены
записей пока нет
ошибка запроса
операция успешно выполнена
~~~

Можно хранить:

~~~javascript
let loading = false;
let errorMessage = '';
~~~

Но не требуется делать сложный фреймворк или архитектуру компонентов. Достаточно понятных функций, которые обновляют DOM.

Проверка:

1. открыли страницу;
2. выключили Node.js;
3. нажали «Обновить»;
4. увидели сообщение об ошибке, а не бесконечную загрузку;
5. запустили сервер снова;
6. повторили запрос успешно.

# 14. Один сервер или два: что такое CORS

В нашем варианте:

~~~text
страница: http://localhost:3000
API:      http://localhost:3000/api/tasks
~~~

Оба адреса имеют одинаковый origin: схема, хост и порт совпадают.

Поэтому особая настройка CORS обычно не нужна.

Если открыть фронтенд с другого порта:

~~~text
страница: http://localhost:5500
API:      http://localhost:3000
~~~

это уже разные origin. Браузер применяет политику одинакового происхождения; для чтения кросс-доменных ответов может потребоваться разрешение CORS на сервере.

**CORS — не замена авторизации и не гарантия безопасности API.**

В основной работе используйте вариант с одним origin. Второй вариант можете изучить отдельно как эксперимент.

# 15. Как отлаживать весь путь запроса

Откройте DevTools → Network → Fetch/XHR.

После нажатия «Добавить» найдите запрос POST и проверьте:

- Request URL;
- Request Method;
- Request Payload;
- Status Code;
- Response.

После PATCH посмотрите JSON с изменёнными полями.

После DELETE убедитесь, что сервер вернул 204.

Если интерфейс не обновляется, проследите всю цепочку:

~~~text
сработал ли обработчик кнопки?
        ↓
отправился ли fetch?
        ↓
какой HTTP-статус?
        ↓
какое тело ответа?
        ↓
изменилась ли база?
        ↓
вызваны ли refreshTasks() и render()?
~~~

Не начинайте отладку с бессистемной замены кода.

# Практическая работа №7. Браузерный интерфейс для собственного API

Создайте папку:

~~~text
internet-technologies/07/
~~~

Продолжите проект ЛР6: существующие Express-маршруты и SQLite должны остаться рабочими.

## Часть 1. Одна точка входа

Сервер должен отдавать HTML, CSS, JavaScript и API с одного origin. Приложение открывается по адресу вида:

~~~text
http://localhost:3000
~~~

На странице есть заголовок, форма создания, список записей и место для сообщений.

## Часть 2. Чтение данных

После открытия страницы выполните GET своего API и выведите список в DOM.

Если записей нет, покажите «Список пуст».

Добавьте кнопку повторной загрузки.

## Часть 3. Полный CRUD через интерфейс

Реализуйте без ручного вызова curl:

- создание записи через форму (POST);
- изменение минимум одного поля (PATCH);
- удаление записи с подтверждением (DELETE);
- получение актуального списка (GET).

Всё должно работать **без полной перезагрузки страницы**.

## Часть 4. Состояние

Используйте отдельный массив данных, например tasks.

Не храните одно и то же значение в нескольких несвязанных переменных. После изменения данных обновляйте интерфейс через render().

## Часть 5. Проверка ввода

Нельзя создавать запись без обязательного поля.

Проверьте отдельно:

- пустую строку;
- строку из пробелов;
- корректный ввод;
- ответ 400 от сервера.

Клиентская валидация улучшает интерфейс, но серверная из ЛР6 должна продолжать работать.

## Часть 6. Ошибки

Обработайте:

- недоступный сервер;
- 400 при некорректных данных;
- 404 при запросе несуществующей записи;
- успешный DELETE с 204 без тела;
- пустой список.

Ошибки показывайте на странице, а не только в console.log().

## Часть 7. Постоянное хранение

Создайте запись из браузера, перезапустите сервер и снова откройте страницу.

Данные должны остаться в SQLite и отобразиться без ручного восстановления.

## Часть 8. Безопасный вывод

Отображайте пользовательские поля через textContent или создание DOM-элементов, а не вставляйте их напрямую через innerHTML.

Проверьте названием:

~~~text
<b>Проверка</b>
~~~

На странице должен появиться текст с угловыми скобками, а не жирная HTML-разметка.
