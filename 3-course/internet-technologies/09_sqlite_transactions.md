# Занятие 9. Транзакции SQLite: целостность данных и атомарные операции

## О занятии

В ЛР6 мы научились хранить записи в SQLite, в ЛР7 построили интерфейс, а в ЛР8 добавили серверный поиск и постраничный вывод.

До сих пор каждое действие обычно меняло **одну запись**. Но реальные приложения часто должны изменить несколько связанных записей одновременно.

Например, пользователь переносит задачу между двумя списками, бронирует место с ограниченной вместимостью или списывает товар со склада и создаёт строку заказа.

Если первая SQL-операция выполнится, а вторая завершится ошибкой, данные могут оказаться в некорректном состоянии.

Сегодня разберём **транзакции**, ограничения SQLite и безопасное выполнение нескольких операций как единого целого.

Продолжаем Express + SQLite + браузерный интерфейс. Для примеров используем \`better-sqlite3\` из предыдущих работ.

---

# 1. Проблема частичного выполнения

Представим приложение с двумя счётчиками остатков.

Нужно перенести 3 единицы из склада A в склад B:

~~~text
A: 10 → 7
B:  5 → 8
~~~

Допустим, мы выполнили уменьшение A, а затем программа упала до увеличения B.

Получилось:

~~~text
A: 7
B: 5
Итого: 12 вместо 15
~~~

Одна бизнес-операция состояла из двух SQL-изменений, но выполнилась только наполовину.

Нам нужно правило: **либо обе операции успешны, либо не происходит ни одна**.

Для этого используется транзакция.

---

# 2. Что такое транзакция и ACID

Транзакция — логическая группа операций с базой данных.

Основные свойства ACID:

- **Atomicity (атомарность):** все изменения применяются вместе либо откатываются.
- **Consistency (согласованность):** ограничения данных сохраняются, если транзакция и бизнес-логика сформулированы корректно.
- **Isolation (изоляция):** параллельные операции не должны видеть недопустимые промежуточные состояния; конкретное поведение зависит от СУБД и режима транзакции.
- **Durability (долговечность):** после подтверждённой фиксации данные сохраняются согласно гарантиям и настройкам SQLite.

SQL-команды:

~~~sql
BEGIN;
UPDATE ...;
UPDATE ...;
COMMIT;
~~~

\`COMMIT\` фиксирует изменения.

При ошибке выполняется \`ROLLBACK\`, который отменяет ещё не зафиксированные изменения транзакции.

# 3. Пример схемы SQLite

Для наглядного задания используем таблицы \`inventories\` и \`transfers\`.

~~~sql
CREATE TABLE IF NOT EXISTS inventories (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  quantity INTEGER NOT NULL CHECK(quantity >= 0)
);

CREATE TABLE IF NOT EXISTS transfers (
  id INTEGER PRIMARY KEY,
  from_id INTEGER NOT NULL,
  to_id INTEGER NOT NULL,
  quantity INTEGER NOT NULL CHECK(quantity > 0),
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (from_id) REFERENCES inventories(id),
  FOREIGN KEY (to_id) REFERENCES inventories(id),
  CHECK(from_id <> to_id)
);
~~~

Что дают ограничения:

- \`PRIMARY KEY\` — уникальный идентификатор;
- \`NOT NULL\` — значение обязательно;
- \`UNIQUE\` — название склада не повторяется;
- \`CHECK(quantity >= 0)\` — остаток не становится отрицательным;
- \`FOREIGN KEY\` — перевод ссылается на существующие склады;
- \`CHECK(from_id <> to_id)\` — нельзя переводить со склада на тот же склад.

В SQLite проверку внешних ключей нужно явно включать для подключения:

~~~javascript
db.pragma('foreign_keys = ON');
~~~

Сделайте это после открытия соединения, до обработки запросов, вне активной транзакции.

---

# 4. Почему клиентской проверки недостаточно

Пользователь может отправить отрицательное количество, строку вместо числа или несуществующий ID.

Даже если в HTML есть \`min="1"\`, запрос можно отправить напрямую.

Сервер должен проверить:

~~~javascript
function isPositiveInteger(x) {
  return Number.isSafeInteger(x) && x > 0;
}
~~~

Для операции переноса нужны:

- \`fromId\` и \`toId\` — положительные целые числа;
- \`quantity\` — положительное целое число;
- разные ID;
- существующие записи;
- достаточный остаток источника.

Не превращайте произвольные строки в числа молча: лучше заранее определить контракт API и явно отклонять неподходящие типы.

# 5. Атомарная операция в better-sqlite3

Библиотека \`better-sqlite3\` предоставляет \`db.transaction(callback)\`.

Подготовим запросы:

~~~javascript
const decrease = db.prepare(
  'UPDATE inventories SET quantity = quantity - ? ' +
  'WHERE id = ? AND quantity >= ?'
);

const increase = db.prepare(
  'UPDATE inventories SET quantity = quantity + ? WHERE id = ?'
);

const saveTransfer = db.prepare(
  'INSERT INTO transfers (from_id, to_id, quantity) VALUES (?, ?, ?)'
);
~~~

Теперь единая операция:

~~~javascript
const transferTx = db.transaction((fromId, toId, quantity) => {
  const source = decrease.run(quantity, fromId, quantity);

  if (source.changes !== 1) {
    throw new Error('SOURCE_UNAVAILABLE');
  }

  const destination = increase.run(quantity, toId);

  if (destination.changes !== 1) {
    throw new Error('DESTINATION_NOT_FOUND');
  }

  const log = saveTransfer.run(fromId, toId, quantity);

  return {
    id: Number(log.lastInsertRowid),
    fromId,
    toId,
    quantity
  };
});
~~~

**Главное:** если внутри callback возникнет исключение, \`better-sqlite3\` откатит всю транзакцию. Успешный выход зафиксирует её.

\`run()\` возвращает информацию об изменениях. \`changes === 1\` позволяет проверить, что обновилась ровно одна нужная запись.

Не выполняйте внутри синхронной транзакции асинхронные операции с \`await\`, HTTP-запросы или длительные действия.

---

# 6. Ошибка посередине и rollback

Пример:

~~~javascript
const demoTx = db.transaction(() => {
  db.prepare('UPDATE inventories SET quantity = quantity - 2 WHERE id = 1').run();
  throw new Error('Имитация сбоя после первого SQL-запроса');
  // второй UPDATE не выполнится
});
~~~

Если вызов \`demoTx()\` завершится исключением, изменение первого \`UPDATE\` будет отменено.

**Не путайте:** откат отменяет изменения, сделанные *внутри этой транзакции*, но не уже закоммиченные операции и не внешние действия (например, отправленное письмо).

На защите сравните остатки до и после имитации сбоя.

# 7. Маршрут POST /api/transfers

Добавим отдельный API-маршрут:

~~~javascript
app.post('/api/transfers', (req, res) => {
  const { fromId, toId, quantity } = req.body ?? {};

  if (!isPositiveInteger(fromId) ||
      !isPositiveInteger(toId) ||
      !isPositiveInteger(quantity) ||
      fromId === toId) {
    return res.status(400).json({ error: 'Некорректные параметры' });
  }

  try {
    const result = transferTx(fromId, toId, quantity);
    return res.status(201).json(result);
  } catch (error) {
    if (error.message === 'SOURCE_UNAVAILABLE') {
      return res.status(409).json({
        error: 'Источник не найден или недостаточный остаток'
      });
    }

    if (error.message === 'DESTINATION_NOT_FOUND') {
      return res.status(404).json({
        error: 'Получатель не найден'
      });
    }

    console.error(error);
    return res.status(500).json({ error: 'Ошибка сервера' });
  }
});
~~~

HTTP 409 означает конфликт с текущим состоянием ресурса (например, недостаточный остаток).

Обратите внимание: если ID получателя отсутствует, первая операция уменьшения могла успеть выполниться — но исключение откатит её.

Коды ошибок являются выбранным здесь контрактом API. Допустимы другие обоснованные решения, если они согласованы между сервером, клиентом и README.

# 8. Проверка целостности и инварианты

**Инвариант** — свойство, которое должно оставаться истинным после успешной операции.

Для переноса:

~~~text
quantity(A) >= 0
quantity(B) >= 0
quantity(A) + quantity(B) = const
~~~

Пример:

~~~text
До:    A=10, B=5, сумма=15
После: A=7,  B=8, сумма=15
~~~

Проверка только HTTP-ответа недостаточна. После запроса прочитайте реальные остатки из SQLite и проверьте сумму.

Полезный SQL:

~~~sql
SELECT SUM(quantity) AS total FROM inventories;
~~~

Ограничения \`CHECK\` и \`FOREIGN KEY\` защищают отдельные правила, но не заменяют всю бизнес-логику.

---

# 9. История операций и журнал

Таблица \`transfers\` хранит историю переводов. Она должна обновляться **в той же транзакции**, что и остатки.

Если остатки изменились, но запись в историю не добавилась, система потеряет согласованность.

Добавьте маршрут:

~~~javascript
app.get('/api/transfers', (req, res) => {
  const rows = db.prepare(
    'SELECT id, from_id, to_id, quantity, created_at ' +
    'FROM transfers ORDER BY id DESC LIMIT 50'
  ).all();

  res.json(rows);
});
~~~

История нужна для контроля и объяснения результата операций. Она не должна вручную «подделываться» на клиенте.

# 10. Интерфейс и обработка ответа

В браузере форма выбирает источник, получателя и количество:

~~~html
<form id="transfer-form">
  <select id="from-id"></select>
  <select id="to-id"></select>
  <input id="quantity" type="number" min="1" step="1">
  <button type="submit">Перенести</button>
</form>
<p id="message"></p>
~~~

Пример отправки:

~~~javascript
async function sendTransfer(fromId, toId, quantity) {
  const response = await fetch('/api/transfers', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ fromId, toId, quantity })
  });

  const body = await response.json();

  if (!response.ok) {
    throw new Error(body.error || 'HTTP ' + response.status);
  }

  return body;
}
~~~

При успешном ответе заново получите остатки и историю, чтобы страница показывала состояние SQLite.

При ошибке покажите понятное сообщение, не изменяя локальные остатки «на глаз».

Используйте \`textContent\` для сообщений и названий, пришедших с сервера.

# 11. Транзакция и несколько пользователей

Два клиента могут почти одновременно пытаться забрать одни и те же остатки.

Проверка «сначала SELECT, затем UPDATE» без согласованной транзакции ненадёжна: данные могут измениться между действиями.

Поэтому в нашем примере условие \`quantity >= ?\` находится **прямо в UPDATE**:

~~~sql
UPDATE inventories
SET quantity = quantity - ?
WHERE id = ? AND quantity >= ?
~~~

Если остатка недостаточно, строка не изменится и \`changes\` будет равно 0.

SQLite допускает только одного писателя одновременно. Тем не менее нужно корректно обрабатывать ошибку занятости/блокировки базы и не считать её успешной операцией.

Для этой лабораторной не требуется создавать распределённую систему или многопоточную нагрузку, но важно понимать, почему проверка остатка должна быть согласована с самим изменением.

# 12. Демонстрационные испытания

Подготовьте тестовые записи A=10 и B=5.

| Ситуация | Ожидаемый результат |
|---|---|
| Перенос 3 из A в B | A=7, B=8, история +1 |
| Перенос 99 из A в B | HTTP 409, остатки и история не изменились |
| Перенос в несуществующий ID | HTTP 404, остатки и история не изменились |
| Один и тот же источник и получатель | HTTP 400, без изменений |
| Количество = 0 / -2 / "abc" | HTTP 400, без изменений |
| Имитация исключения после первого UPDATE | Полный rollback |
| Повторный запрос после ошибки | Новая корректная операция работает |
| Перезапуск сервера | Остатки и история сохраняются |

**Важно для испытания сбоя:** тестовый механизм сбоя должен включаться только локально и не оставаться в рабочем API. Можно проверить откат отдельным тестовым скриптом, использующим ту же функцию-транзакцию с контролируемым исключением.

# Практическая работа №9. Атомарная операция из нескольких SQL-запросов

Создайте папку:

~~~text
internet-technologies/09/
~~~

Продолжите проект ЛР8: API, SQLite, поиск, сортировка и пагинация должны остаться рабочими.

## Часть 1. Схема и инвариант

Выберите собственный сценарий **с несколькими связанными изменениями**:

- перенос количества между складами;
- перевод товара между местами хранения;
- бронирование места с уменьшением доступного количества и записью брони;
- создание заказа со списанием остатков и записью строк заказа;
- аналогичная операция для своей сущности.

Если используете другую предметную область, согласуйте инварианты и ограничения в README. Простого изменения одной строки без зависимой второй операции недостаточно.

## Часть 2. Транзакция

Реализуйте атомарную операцию из **минимум двух связанных SQL-изменений**; кроме них желательно записывать историю в третью таблицу.

Используйте \`db.transaction()\` или корректные SQL \`BEGIN/COMMIT/ROLLBACK\`.

## Часть 3. Ограничения

Добавьте подходящие ограничения базы: \`NOT NULL\`, \`CHECK\`, \`UNIQUE\`, \`FOREIGN KEY\` (где применимо). Включите проверку внешних ключей.

Проверяйте значения входных параметров на сервере. Обрабатывайте 400, 404, 409 и непредвиденные ошибки без раскрытия внутренних сообщений SQLite клиенту.

## Часть 4. Интерфейс

Создайте форму операции. После успеха она обновляет связанные данные и журнал из SQLite. После ошибки показывает сообщение и оставляет отображение согласованным с сервером.

Приложение продолжает работать через один origin Express, без полной перезагрузки.

## Часть 5. Проверка rollback

Продемонстрируйте ситуацию, когда первая SQL-операция могла бы выполниться, а следующая не выполняется. В результате **ни одна операция транзакции не должна остаться в базе**.

Покажите данные до и после отката, включая журнал.

## Часть 6. Дополнительные проверки

- корректная операция;
- нехватка ресурса;
- несуществующая связанная запись;
- недопустимый тип/значение;
- запрет операции с одинаковым источником и получателем, если сценарий это предполагает;
- сохранение после перезапуска;
- корректное отображение ошибок;
- сохранение инварианта при серии успешных операций.
